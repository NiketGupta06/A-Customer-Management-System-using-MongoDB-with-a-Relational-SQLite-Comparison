Relational Model

Paper Concepts Demonstrated

Each module maps to a key claim from the MongoDB white paper

DATA MODEL

Intuitive Data Model

All customer data lives in one JSON document — name, addresses, phones, interests — instead of being scattered across 4 SQL tables.

CRUD

Native CRUD Operations

Add, view, update, and delete customers using PyMongo. The $push operator adds a phone number without rewriting the entire document.

SCHEMA

Flexible Schema

Three customers with entirely different field structures stored in one collection — no ALTER TABLE required.

GOVERNANCE

Schema Validation

JSON Schema rules enforce required fields and data types. Valid documents pass; invalid ones are rejected at the database level.

QUERIES

Powerful Queries & Aggregation

Filter by nested fields, query arrays, and run aggregation pipelines to group customers by city with spend statistics.

PERFORMANCE

Indexing Performance

Query 50,000 documents with and without an index. Measured a 2.2× speed-up — with network latency to Atlas included.

TRANSACTIONS

ACID Transactions

Place an order and reduce stock atomically. If stock is insufficient, the entire transaction rolls back — nothing changes.

MongoDB vs SQL — Side by Side

The same customer stored two different ways

MongoDB — 1 document 
{
  "customerID": 12345,
  "name": {"first": "John", "last": "Doe"},
  "address": [{
    "city": "London",
    "street": "16 Hatfields"
  }],
  "email": "john.doe@acme.com",
  "phone": [{"number": "+44-1234567890"}],
  "interests": ["devops", "data science"],
  "annualSpend": 1292815.75
}
SQL — 4 tables, 3 JOINs 
SELECT c.first_name, c.last_name,
       a.city, p.number, i.subject
FROM customer c
JOIN address  a ON a.customer_id = c.customer_id
JOIN phone    p ON p.customer_id = c.customer_id
JOIN interest i ON i.customer_id = c.customer_id
WHERE c.customer_id = 12345;

-- Returns DUPLICATE rows due to
-- phone × interest cross product
Feature SQL (SQLite) MongoDB
Tables / collections for one customer 4 tables 1 collection
JOINs to read a customer 3 JOINs 0 — single find()
Adding a new field ALTER TABLE required Just insert it
Data stored Spread across rows Single document
Schema Fixed upfront Flexible + optional validation
Array operations Separate table + INSERT $push / $pull in-place

Indexing Performance — 50,000 Documents

Query: find customer by email in a collection of 50,000 documents

Without Index
57.91 ms
With Index
26.67 ms
~2.2× faster with a single-field index on email
Note: The 2.2× gain is modest because network round-trip latency to MongoDB Atlas (cloud) is included in both measurements. On a local MongoDB instance, the gap would be significantly larger since index lookups are O(log n) vs. a full collection scan at O(n). The important takeaway is that even over the network, indexing provides a measurable improvement.
